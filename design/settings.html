Decisions and how they fit the system

Why this layout

  • The headline sentence states the result of the settings (a 59-day reorder line), so staff see what changing a number does.
  • Defaults first, then per-product overrides, because that is the order in which the SOP defines them.
  • Placeholders show the default, so "blank means default" needs no explanation.
  • Save is the one filled button. Destructive actions stay outlined and live inside the modal.

How it connects to the code

  • Settings holds one row of defaults. Product.lead_time, safety_days and target_days are the overrides, empty means default. forecast.py already takes these as arguments.
  • Identifiers and bundle_map feed the sales matching that the seed and import already use.
  • The Outbox page lists the Outbox table. The alert test writes one row.
  • The stale warning compares Settings.data_updated_at with today, in store time.

Rules and honest limits

  • Test mode is permanent for this assignment. The page says so, and there is no field for a mail password, so no secrets live in the repo.
  • Changing a forecast default changes every product without an override at once. The save button label does not hide that.
  • Deleting a product with history is blocked and offers Archive. Archive is a small addition to the model and goes in the design note.
