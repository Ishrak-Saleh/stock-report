Decisions and how they fit the system

Why this layout

  • Suppliers get a smaller app, not a locked copy of the big one. Fewer tabs means fewer wrong taps.
  • The headline puts the thing they owe us first: confirm, then tracking.
  • The "can and cannot" panel is on the page once so a supplier never wonders why Edit is missing.
  • Errors keep the top bar. A 403 explains the cause in plain words instead of a code alone.

How it connects to the code

  • User already has role and supplier_id. A session cookie holds the user id, signed with a key read from the environment, never the repo.
  • Two FastAPI dependencies, require_user and require_staff, guard routers. Supplier requests are filtered by supplier_id in services/orders.py, so hiding a button is never the only protection.
  • Every form carries a CSRF token. Responses add security headers. Passwords are hashed.
  • OrderEvent.by becomes the signed-in person's name, which fixes the placeholder name in history.

Rules and honest limits

  • The supplier's Confirm and Add tracking write the same events as staff do, labeled with the supplier's name.
  • Tracking units cannot exceed the order total, checked in domain/orders.py.
  • Login throttling and session length are simple and in-memory. Good for a demo, and the design note says so.
  • The supplier cannot see forecasts. That is a deliberate choice, since forecasts hold the buyer's own planning.
